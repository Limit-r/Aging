## 1. 本次会话完成内容

### 1.1 torchao 定性弃用（源头已堵死）
- 现象：`pip install torchao` 可装（0.18.0），但 `import torchao` 直接崩。
- 根因：torchao 0.18 要求 **torch≥2.11**，当前环境是 **torch 2.8.0+cu128**，报 `ImportError: cannot import name 'ScalingType' from 'torch.nn.functional'`。
- 结论：**不依赖 torchao**，走「自定义 Quantizer + torch2.8 内置 pt2e」路线（已在 memory、spike 验证过）。torchao 可留可卸，无副作用。

### 1.2 正式 QAT 模块 `ml/train/qat_quantizer.py`（新增）
- `ConvSiluQuantizer(Quantizer)`：对每个 `aten.conv2d`/`aten.convolution` 节点标注
  - 权重：per-channel symmetric INT8（`MovingAveragePerChannelMinMaxObserver`）
  - 激活：per-tensor affine UINT8（`MovingAverageMinMaxObserver`）
  - QAT fake-quant 用 `FusedMovingAvgObsFakeQuantize`
- `prepare_qat(model, example_input, quantizer=None)` → `(prepared, quantizer)`
  - **含惰性缓存预热**：YoloBody 的 `anchors/strides/shape` 是 forward 内延迟生成的实例属性，`torch.export` 拒绝在 traced forward 里新建属性 → 必须先跑一次前向物化再 export（`prepare_qat` 内已做 no_grad 预热 + 恢复 train/eval）。
  - **内置 `allow_exported_model_train_eval`**：pt2e 导出的模型默认禁用 `.train()/.eval()`，放开后才能在现有训练循环里用。
- `convert_qat(prepared)` → 含 QDQ 算子的 GraphModule（用 `convert_pt2e`）。
- `count_quant_nodes(gm)` → `{"fake_quant": n, "q_dq": n}` 供日志/校验。

### 1.3 `ModelEMA` 新增 `param_only` 选项（`ml/model/yolo_training.py`）
- 问题：标准 EMA 会把 fake-quant 观察器 buffer 也做 EMA，权重观察器 scale 是 per-channel `[16]`、激活观察器 `min_val` 是 per-tensor `[1]`，键错位 → `RuntimeError: output with shape [1] doesn't match the broadcast shape [16]`。
- 修复：`param_only=True` 时 EMA 只平滑**可学习权重参数**（按 `named_parameters()` 键过滤），跳过量化观察器 buffer。观察器统计应反映最新分布，本就不该被 EMA 平滑。
- **普通（非 QAT）训练不受影响**（默认 `param_only=False`，行为不变）。

### 1.4 `train.py` 接入 QAT（`ml/train.py:train()`）
关键改动点：
1. `qat = cfg.get('qat', False)`；开启时**强制 `fp16=False`**、**强制 `Freeze_Train=False`**（图模块无 `backbone` 属性，冻结阶段会崩）。
2. `yolo_loss = Loss(model)` **必须先于 QAT 转换创建**（`Loss` 读 `stride/no/reg_max`，这些只存在于原始 `YoloBody`）。
3. QAT 转换放在 yolo_loss 之后：
   ```python
   from train.qat_quantizer import prepare_qat
   model, qz = prepare_qat(model, (torch.zeros(1, 3, *input_shape, device=device),))
   ```
4. CUDA 封装**走单卡**：QAT 图模块是图级参数，不包 `DataParallel`。
5. `ema = ModelEMA(model_train, param_only=qat)`。
6. 优化器仍用原有 `named_modules` 拆分——已验证图模块能正常暴露 64 个卷积权重参数，外围逻辑无需改动。

### 1.5 训练入口与配置
- `ml/train/train_merged.py`：新增 **`--qat`** 参数（`action='store_true'`），开启后打印 QAT 开关状态。
- `ml/train/config_merged_train.json`：新增 `"qat": false`（**默认关闭，不影响现有 FP32 训练**）。

## 5. 关键坑位 / 经验（务必记住，别再踩）

1. **conda 环境名大小写**：`Aging`（大写）。`conda activate aging` 会报 `EnvironmentNameNotFound`，直接用 `E:\MiniConda\envs\Aging\python.exe` 最稳。
2. **torchao 0.18 与 torch2.8 不兼容**，别再去装/纠结它。
3. **导出前必须预热前向**物化 anchors/strides，否则 `torch.export` 报 `ValueError(...must be registered as buffer)`。
4. **pt2e 导出模型默认不让 train/eval**，必须 `allow_exported_model_train_eval`（已内置到 prepare_qat）。
5. **QAT 的 EMA 只平滑权重**（`param_only=True`），否则 per-channel/per-tensor 观察器 buffer 形状错位崩溃。
6. 真实 `yolo_dataset_collate` 输出的 batch 是 **(总框数, 5)** 扁平张量，不是 `(bs,maxbox,5)`——所以 `Loss` 里 `batch[:,0].view(...)` 才能成立。
7. **QAT 训练 4 处真坑（`ml/train.py`，2026-08-25 实测修复）**：
   - 设备不匹配：`prepare_qat` 内部会先跑一次真实前向预热惰性缓存，若模型还在 CPU、示例输入用了 cuda → `Input type(cuda) vs weight(cpu)`。**QAT 转换前先 `model.cuda()`**。
   - `train()` 返回 None：`allow_exported_model_train_eval` 覆盖的 `train()` 不返回 self，`model_train = model.train()` 得 None → 后续 `.cuda()` 崩。**QAT 分支改 `model.train(); model_train = model`**。
   - 优化器参数组：QAT 图模块 BN 已 fold（`.bn` 子模块无 weight，卷积权重变成 `*.conv.weight_bias`），且 `pg0` 为空。**`"bn" in k` 需同时 `hasattr(v,"weight")`；`pg0` 空时用 `pg1`（带 weight_decay）作 optimizer 基组**。
   - batch 尺寸固化：`torch.export` 把示例输入 batch 固化为常量 **1**，训练 batch=2 时 DFL 解码 `view([1,4,16,5376])` 元素数不符直接崩。**QAT 示例输入 batch 必须用训练实际 batch**（Freeze 下 `Freeze_batch_size`，否则 `Unfreeze_batch_size`）。
8. **ONNX 数值校验的判定基准**：纯 FP32 全模型导出与 ONNX Runtime 逐元素一致（dbox diff 9.5e-07、cls 0）→ 说明导出/ORT 链路可靠，差异只可能来自量化路径。

## 6. 已知事项 / 遗留（明天重点）

### 6.1 QDQ ONNX 导出 + 数值差异根因：**已闭环，结论=期望行为，非 bug**
- **产物**：`ml/train/export_qat_onnx.py` 产出 `ml/deploy/yolo_qat_int8.onnx`（batch=1、512²、输出仅 dbox/cls，714KB），`onnx.checker` 通过。
- **端到端推理已打通**：`ml/train/infer_qat_onnx.py` 用 onnxruntime 跑通该 ONNX → 解码(DecodeBox) → NMS → 可视化，检出 FP_VPL/FP_CPL/FP_SIG_area 等，输出 `detect/outputs/onnx/vis_*.jpg`。
- **数值差异（dbox ~0.38 / cls ~2.7）——根因已定性为「部署引擎真 INT8 vs 训练侧 FP32 模拟」，是预期且有利的行为，不是导出 bug**。证据链（全部实测）：
  1. 纯 FP32 全模型导出与 ORT 逐元素一致（dbox 9.5e-07、cls 0）→ 导出/ORT 链路、所有非量化算子（conv/bn/silu/DFL）可靠。
  2. 单 Q→DQ 算子级对拍：torch 的 quantize/dequantize 与 ONNX QuantizeLinear/DequantizeLinear（per-tensor 激活）**完全一致（diff=0）**。
  3. per-channel 权重 DQ 的 scale/zp 常量 ONNX 与 GraphModule **逐值一致（diff=0）**（GraphModule 64 权重 DQ、ONNX 63——后者待核，但首层一致）。
  4. 逐层对拍：**第 0 层 stem conv 即有差异**，且该层 ONNX/GraphModule 结构同源（输入=`dequantize_per_tensor`、权重=`dequantize_per_channel`、+`weight_bias`），两图 DQ→Conv **直接相连** → ORT 必然把 DQ-Conv-DQ 融合成 **真正 INT8 内核（QLinearConv）**；GraphModule 是 **FP32 模拟 QDQ**。
  5. 不同 ORT 优化级别（DISABLE_ALL/ENABLE_BASIC/EXTENDED/ALL）diff **完全相同** → 与图变换无关，是 op kernel 选择（QDQ 模型必走 INT8 内核）的固有差异。
  - **含义**：ORT/TensorRT 侧就是**真正的 INT8 量化推理**（更快），GraphModule 是**训练侧 FP32 模拟参考**。两者不同**是正确且应当的**；若强行让 ORT 与 GraphModule 逐元素对齐，反而会失去 INT8 加速。真正该对比的是「部署侧与 FP32 原始模型的 mAP 精度」，而不是「ORT 与 GraphModule 逐元素一致」。
- **本机 TensorRT 攻坚受阻（环境硬限制，非代码问题）——已拍板暂缓 TRT，以 ONNX INT8 为部署基线**：
  - 本机 GPU RTX 5060 Ti（Blackwell sm_120，8GB）、CUDA 驱动 13.0、PyTorch 2.8+cu128。
  - 已**穷举全部 Windows 端自动获取 TRT 二进制的通道，全部堵死**（均实测）：
    1. NGC pip `pypi.ngc.nvidia.com` → **DNS 解析失败**（本机/网络层直接不返回，非临时抖动）。
    2. NGC NuGet `nuget.ngc.nvidia.com` → 同一证书域名，同样不可达。
    3. conda `nvidia` 通道 → **Windows 上无 tensorrt 包**（该通道 TRT 仅发布 Linux）。
    4. 常规/清华 PyPI → 仅有 ~18KB 的 sdist 包装（`gitlab-pip` metapackage），**实际二进制仍在构建时回跳 NGC**，不解决根因。
    5. nuget.org → 无 `Nvidia.TensorRT` 包（BlobNotFound）；本机磁盘也无已装的 `nvinfer*.dll` / `trtexec.exe`。
  - 官方开发者下载（`developer.download.nvidia.com` 可达）需**登录 + 授权**，无法脚本化自动化。
  - Blackwell 需 TensorRT ≥10.6 + 匹配 CUDA Toolkit。**结论：本机（5060 Ti）不具备 TRT 离线安装条件**。**决策：暂缓 TRT，先把 QDQ ONNX 经 ORT 的真 INT8 推理（已跑通、检测正常）作为部署基线**；待部署主机具备自动直连 NGC 的网络/官方预装 NVIDIA stack 后再攻关 TRT INT8 合成与下发（建议放低配方案 B：RTX 3050 On）。

## 8. 决策变更（2026-08-25 下午）：由「QAT 重训保精度」改为「PTQ 直接量化」

### 8.1 背景
此前为了把 INT8 精度拉回，尝试把 QAT 训练放宽到 200 轮并开启 mAP 评估（`config_cmp_qat.json`，save_dir=`weights/MERGED_CMP_QAT_V2`）。实测暴露两个问题：

1. **终端直跑必崩（坑位）**：`train.py` 评估后打印 `🔍🏆🎯` 等 emoji 到中文 Windows 的 GBK 控制台会触发 `UnicodeEncodeError: 'gbk' codec can't encode '\U0001f50d'`，导致训练在首个/每次评估打印处退出。GUI 因注入 `PYTHONIOENCODING=utf-8` 不崩；裸终端必须设 `PYTHONIOENCODING=utf-8` + `PYTHONUNBUFFERED=1`。
2. **QAT 收敛极慢**：QAT 从零起步（初始 loss 也达 1118，与 FP32 相同的从头起点），但到第 50 轮 mAP 仍只有 ~0.02；而 FP32 同任务约 30 轮即达 0.988。QAT 更慢，放宽到 200 轮不保证拉回精度，代价高（数小时）。

### 8.2 决策：PTQ（训练后量化）取代 QAT 路径
既然已有训好的 FP32 模型（`weights/MERGED_CMP_FP32`，mAP 0.988），且部署基线本就是 ONNX INT8（TRT 在 Windows 拿不到），改为**基于 FP32 做 PTQ 校准量化**，无需重训。

- 新增 `ml/train/ptq_onnx.py`：重载 FP32 → `prepare_qat`（复用 `ConvSiluQuantizer`）→ **校准**（64 张 val 图前向收集观察器统计）→ `convert_qat` → 导出 QDQ ONNX INT8。
- 产物 `ml/deploy/yolo_ptq_int8.onnx`（727642 B ≈ 727KB，输入 `[1,3,512,512]`，输出 `dbox(1,4,5376)`+`cls(1,9,5376)`），`onnx.checker` 通过。
- 数值校验：dbox max_abs_diff=1.04 / cls=0.68（ORT 真 INT8 vs 转换图 FP32 模拟，期望差异，见 6.1）。

### 8.3 FP32 vs INT8(PTQ) 实测精度（test 集 68 张，conf=0.05，nms=0.45）
| 后端 | mAP | 检测框 |
|------|------|--------|
| FP32（PyTorch） | **99.02%** | 802 |
| INT8（PTQ，ORT 真 INT8 内核） | **98.96%** | 804 |
| 绝对差 | **0.06pp** | — |

**结论：PTQ INT8 相对 FP32 基本无损（loss<1pp）。** 相比 QAT 200 轮重训的缓慢/不确定，PTQ 几分钟完成且保留 ~99% mAP，为当前 ONNX INT8 部署的更优基线。

## 10. 动态 batch（ONNX GPU 方案推进）（2026-08-25 晚）

### 10.1 背景与根因
- **GPU 方案的目标**：让 54 路静默监控在 ONNX INT8 上获得批量吞吐（目标 54×4fps=216fps）。
- **阻塞点**：`ptq_onnx.py` 导出的 ONNX 是**固定 batch=1**，使引擎 `_onnx_decode` 只能逐帧 `sess.run`（旧代码逐帧循环）→ 批量吞吐只有 ~72fps（batch=1）。
- **为什么不能直接动态 batch 导出**：YoloBody 的 DFL 让 `torch.export` 在 CUDA 下做动态 batch（`Dim DYNAMIC`）崩溃（已在 `qat_quantizer.prepare_qat` 注释 + memory 记录）。batch 被固化进**图的 Reshape shape 常量**（如 `[1,4,16,5376]`、`[1,73,-1]`）。

### 10.2 解法：绕开 torch.export，直接改 ONNX 图（`ml/train/dynamicize_onnx.py` 新增）
不重导出，对已导出的固定 batch=1 QDQ INT8 ONNX 做「动态 reshape 注入」：
1. 放宽 input `images`/output `dbox`/`cls` 的 batch 维为符号 `N`。
2. 找出图里 batch 被固化为 1 的 Reshape shape 常量（5 处），改为运行时动态计算：
   - `Shape(images) -> Gather([0]) -> N`；
   - `Concat([N, 其余维度常量])` 作为 Reshape 的 shape 输入（其余维度保留原 `-1`，故每个 Reshape 仍只有一个 `-1`，合法）。
   - 注入节点插在该 Reshape **之前**（保持拓扑序，否则 onnx.checker 报未排序）。
3. 产物 `ml/deploy/yolo_ptq_int8_dyn.onnx`（自包含单文件，~3.75MB，输入 `[N,3,512,512]`）。

**用法**：`E:\MiniConda\envs\Aging\python.exe ml/train/dynamicize_onnx.py`（默认 src=`deploy/yolo_ptq_int8.onnx` → out=`deploy/yolo_ptq_int8_dyn.onnx`，自校验批量 1/4/16）。

### 10.3 引擎接入（`ml/vision/engine.py` 修改）
- `deployed_paths()["onnx"]` 指向 `yolo_ptq_int8_dyn.onnx`。
- `_onnx_decode` 改为**单次动态 batch `run`** 整批（`self.ort_session.run(self.ort_out, {self.ort_in: self._onnx_blob(frames_bgr)})`），不再逐帧循环。

### 10.4 实测结果（RTX 5060 Ti, torch2.8+cu128, ORT1.23.2, CUDA EP）
| 项 | 结果 |
|----|------|
| CUDA EP 生效 | 是（providers = CUDAExecutionProvider, CPUExecutionProvider） |
| 动态 batch | batch=1/4/16 输出形状正确（dbox [B,4,5376], cls [B,9,5376]） |
| 数值（batch=1 切片 vs 单跑） | 0.0px 完全一致（diag 全 14 框 0.0px） |
| 批量吞吐（512² INT8，8 帧） | batch=1 **115 fps** → batch=8 **180 fps**（1.56×） |
| 正确性 | 逐帧 vs 批量检测：数量/类别一致，个别框 ≤1–2px 抖动（INT8/FP32 GEMM 批间固有数值波动，非 bug） |

> 注：批量内个别框有 batch 相关的 1–2px 微抖，源自非量化 FP32 头（DFL/decode）叠加 INT8 激活量化后的浮点累加顺序差异（与此前 QTQ/GraphModule 差异同源）。不影响 LED 亮灭分类（ROI 裁剪偏移极小）与闪烁计数；已在测试脚本中用「最近邻匹配」复核，避免与「同名同坐标框被 set 去重」的误报混淆。

### 10.7 320² 监控模型落地（已闭合 216fps）
**结论先行**：GPU 方案验证通过。320² INT8 动态 batch 在 RTX 5060 Ti（CUDA EP）batch=54 达 **~397fps**，为 54×4fps=216fps 目标的 **1.84×**，批量余量充足。

- **为什么 batch≥8 后 512² 卡在 ~175fps**：继续增大 batch 收益上不去，瓶颈在 8400 锚点的解码+NMS 后处理（batch 只摊平前向）。并行 NMS（`detect_batch_parallel` 8/16 线程）实测无提升 → 瓶颈不是线程，是单帧解码量（5376 锚点）。→ 降到 320²（2100 锚点，约 1/4）即翻倍吞吐。
- **导出**：`ptq_onnx.py --input-shape 320,320` → `deploy/yolo_ptq_int8_320.onnx`（728KB，输入 `[1,3,320,320]`，dbox `(1,4,2100)` + cls `(1,9,2100)`）→ `dynamicize_onnx.py` → `deploy/yolo_ptq_int8_320_dyn.onnx`（动态 batch）。
- **关键坑位**：换输入分辨率后**必须让 decodebox 用匹配的 input_shape 重建**，否则 `decodebox` 仍按 512 生成 5376 锚点网格、与 2100 输出错位（报「anchor数量不匹配 (生成:5376, 模型:2100)」，坐标错误）。引擎 `__init__` 里 `_load_onnx`（先）覆盖 `self.input_shape` 后再构建 `decodebox`（后）→ 只要部署 onnx 指向 320 版，自动正确。测试里二次调用 `_load_onnx` 则需手动重建。
- **正确性**：320² 重建 decodebox 后 `同帧批量 8 元素一致=是`，与 512² 同帧同为 **14 框** → 320² 未丢小目标，检测正确。
- **引擎接入（`ml/vision/engine.py`）**：
  - `deployed_paths()` 新增 `"onnx_mon"` → `yolo_ptq_int8_320_dyn.onnx`；`"onnx"` 仍为 512² 动态版（交互/视频检测保精度）。
  - `DetectionEngine.__init__` 新增 `onnx_path: str | None = None`：指定则强制 onnx 后端并用该模型。
- **监控路由（`ml/vision/worker.py handle_monitor`）**：监控引擎传 `onnx_path=deploy/yolo_ptq_int8_320_dyn.onnx`，配合已有 `MONITOR_INPUT_SHAPE=(320,320)`，与 `detect_batch_parallel(MONITOR_WORKERS=12)` 一起支撑 54 路。交互调度 `handle_video` 等仍用默认 512²。
- **manifest**：`latest.json` 已登记 `onnx`(512²)+`onnx_mon`(320²) 及实测 fps。

**实测吞吐（CUDA EP）**：

| 512² |  99 fps |  174 fps |  178 fps |  178 fps |  173 fps |
| 320² | 131 fps |  335 fps |  381 fps |  403 fps | **397 fps** |
